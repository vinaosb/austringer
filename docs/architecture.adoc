[[architecture]]
== One daemon, four thin clients

The system has exactly one owner of state: the `harness-daemon` process. It
hosts the agent loop, the event log, the session store, the permission
engine, the scheduler, and the sandbox policy. Everything a user touches is
a thin client:

[cols="1,3,1"]
|===
|Client |Role |Code

|CLI
|Headless one-shot `run`/`capture`, interactive REPL, `attach` event tail,
`doctor` health checks, and `--output-json` NDJSON output that doubles as
the eval-adapter contract.
|harness-cli

|TUI
|Event-driven ratatui interface (no polling, no timers on the render
thread): context gauge, cache-hit and cost HUD, omnibar, hunk review gates.
|harness-tui

|Web
|A dashboard SPA served by the daemon itself — no node server, no cloud
dependency. Live session view, hunk review, cost/cache/context dashboards.
|harness-web (static assets)

|VS Code
|TypeScript thin client over the same protocol: native diff decorations,
per-hunk code lenses, opt-in editor telemetry.
|harness-vscode (not a Cargo crate)
|===

Both carriers are loopback-only and authenticated: HTTP/WS/SSE on
`127.0.0.1` with a generated token (the daemon refuses non-loopback binds),
plus a local-socket IPC carrier for terminal clients. Multiple clients may
attach to one session at the same time, and a permission answered by any
client applies to all of them.

The design rule from the research file: one engine, four surfaces, no logic
duplicated into a frontend (research §1 frontends row; crush's multi-client
shared permission queue, research §1).

[[turn-dataflow]]
== The data flow of a turn

. A client submits a prompt over the carrier; the daemon creates or resumes
a session (lazy turn paging from the sessions store) and appends the user
event to the append-only log.
. The agent loop runs its named-operation pipeline (entry hooks, slash
commands, steering, compaction check, tool approval, execution, retry,
stop hooks, inference) — every operation is cancellable mid-flight.
. Tool calls pass the inspector chain (permissions, repetition detection),
run inside the sandbox policy, and land their results through the
byte-capped observation path (spill files for oversized output).
. The prompt builder renders a byte-stable prefix (the context epoch);
streaming inference events fan out to every attached client through the
typed event schema with monotonic ids and bounded replay.
. Snapshots record the pre-turn state so `/rewind` restores files and
history together.

[[design-rules]]
== Design rules with receipts

* No silent model substitution — fallback hops ask the user; model identity
is a contract (research §13, §16, §2).
* No embeddings or vector search for code — lexical index plus AST map by
scope decision (research §1 repo-map rows).
* No whole-file rewrites — windowed views, AST-validated hunks, hash
anchors (research §1 windowed-file-view rows).
* No unstable serialization — sorted keys, stable paths, byte-identical
prefixes; cache-control engineering with a violation tracker (research
§27, §32).
* No orphaned processes — kill trees via Job Objects and PDEATHSIG; the
daemon's crash never leaves tool processes behind (research §1).
* No unverified third-party code running automatically — quarantine,
lock.json ledger, trust gates (research §27).
* Windows is first-class, not an afterthought (research §1 OS-sandbox
rows).
