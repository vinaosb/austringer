2. harness-daemon/src/search.rs (new module, the todo-11 surface):
   - GET /sessions/search?q=<fts5>&limit=N&sessions=a,b — cross-session over the
     daemon's ONE store root (per-request SessionStore::open at data_dir, the
     RunHistory/AutomationStore convention). Empty result = 200 + [] (bare array,
     the history-route precedent). BadQuery => typed 400 {"error":{"code":"bad_query",
     "query","detail"}}; missing q => typed 400 missing_query. limit default 20,
     cap 100.
   - SearchSessionsTool (model-facing `search_sessions` ToolProvider): registered
     via ToolRegistry::register in CoreExecutors::open_registry (the task-3
     per-session registry) — session-scoped BY DEFAULT (scope = the session dir's
     own id; store root derived by rewind.rs's sessions_root, now pub(crate));
     cross-session requires explicit session_ids; limit default 8, hard cap 25
     (requested limit clamped). BadQuery => ProviderError::InvalidArguments (typed,
     model-correctable). NO path argument exists anywhere => no search can cross
     working-dir roots (provider-egress boundary is structural).
   - server.rs: one route line; lib.rs: mod search; tools/providers.rs: str_arg/
     optional_u64_arg made pub(crate) for reuse.
3. harness-cli:
   - `harness sessions search [--limit N] [--sessions a,b] <query>` (cli.rs
     Sessions/SessionsCommand::Search + src/sessions.rs flow + bin dispatch).
     HTTP-only: IPC has no HTTP base and the daemon does not persist its port, so a
     missing --url is a typed transport hint raised BEFORE Target::resolve (else it
     would surface as a misleading token-file failure). 200 => ranked lines / "no
     hits" + exit 0; 400 => typed "protocol error: status 400: bad query: ..." exit 1.

RANKING NOTE (honest deviation):
  The plan's QA prose says "recency-weighted bm25". The binding instruction
  (References) is "reuse meta.rs's MATCH/bm25/snippet/rank idiom", which is pure
  bm25 (ORDER BY rank); event_fts carries no timestamp column to weight by, and
  inventing a recency blend would diverge from the mandated idiom and require a
  schema change on a SELECT-only task. Ranking shipped = bm25 ascending (best
  first, term-frequency weighted). Recorded here and in issues.md for the
  orchestrator.
