## Pathology analysis (measured on this machine, Windows 11, conhost current)
(a) HEADLESS wait/read hang: portable-pty 0.9's ConPTY reader is a plain duplicated
    pipe handle in a BLOCKING ReadFile (no shutdown channel in filedescriptor 0.8.3 -
    verified by reading both crates' sources). T19 detached a still-blocked reader
    after 3s => thread+handle leak per stuck run. Fix = ordered teardown: job kill
    (tree dead) -> writer close (conhost input-thread EOF) -> master close on a
    bounded thread (ClosePseudoConsole tears conhost down => pipe EOF => the blocked
    reader returns) => reader JOINED. Fixture: 10 quick headless runs, each < 8s,
    reader_joined=true every round (QA timings: runs 0.34-2.9s, total 9.48s), plus a
    grandchild-holding-pipe variant (start /b ping + exit 0) that still joins.
(b) Arc shutdown assertion / mid-run drop: the assertion class is portable-pty's
    inner Arc<Mutex<Inner>> teardown racing a live child (its lock().unwrap()s poison-
    panic, and ClosePseudoConsole-while-client-alive). Fix = TreeAndMaster RAII:
    KILL_ON_JOB_CLOSE job close FIRST, master close strictly after, writer in between;
    close runs on a bounded thread so even a wedged teardown cannot hang the run.
    Fixtures: pre-cancelled token vs 120s active tree x10 rounds (all Cancelled,
    bounded, zero orphans by PING.EXE enumeration, reader joined) + 4 concurrent
    active runs tearing down simultaneously (no deadlock, no panic).
(c) DA1 ESC[c 60s hang - MEASURED, JUSTIFIED: the hang has TWO flows. Flow A
    (conhost->terminal queries on the master read side) is answered by the reactive
    responder in pump latency - this is why anything runs through ConPTY at all (T19's
    original hang measurement). Flow B (a CHILD writing ESC[c) is answered BY conhost
    itself in ~0ms: observed live during fixture development - the reply
    ESC[?61;6;7;21;22;23;24;28;32;42c is injected into the console input buffer and
    echoed to the screen as caret-notation text. PROACTIVE PRE-INJECTION REJECTED:
    flow A is already ms-fast, and pre-injecting a reply for flow B would feed stray
    keyboard input to every child that never queries. Fixtures pin both: child
    writes DA1+DSR, reads replies via [Console]::ReadKey (the way VT-aware apps
    read), completes < 5s with replies seen (conhost self-answer path B), and the
    responder's matching is unit-pinned in src/query.rs (flow A). First fixture draft
    used $stdin.Read (line-buffered) - it blocked BECAUSE the reply carries no
    newline; that failure mode is documented here as the measurement evidence.

  never observed in any run; fixtures assert against it)

  relay (WSL session teardown) but that is WSL behavior, not our kernel guarantee -
  documented; the T26 sandbox owns cross-boundary enforcement

  gap, T26's enforcement point (unchanged this round)
