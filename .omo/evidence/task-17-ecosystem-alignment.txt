DESIGN DECISIONS (with rationale)
---------------------------------
1. Execution lane: executor-#3 pattern = the todo-4 safety gate reused
   VERBATIM (tools::safety::gate: policy validation + deny-all egress verdict
   + requested-vs-enforced report) + the policy's EnvScrub applied at the
   spawn seam (scrub_env -> env_clear + envs(kept), exactly what
   ExecSpec.env_scrub does at the PTY seam). Spawn mechanics mirror the
   harness-media tool lane (std::process headless capture + kernel kill-tree
   domain) rather than the PTY screen-delta lane, because the parser needs
   the runner's FULL stream: the PTY grid is bounded by construction
   (head+tail transcript + 75-line window law) and silently loses per-test
   lines on any real suite. Kill tree: Windows Job Object
   KILL_ON_JOB_CLOSE (win32job), Unix process_group(0) + killpg — the
   media-lane thin copy of todo-19's TreeGuard (exec's guard takes a PTY
   child). Todo-4's issues.md note ("todo 17 should reuse
   tools::safety::gate + ExecSpec.env_scrub verbatim") is honored: gate is
   the same function; the scrub is the same policy object applied at the
   equivalent seam of the chosen lane.
2. Gate seam: the override command line is verdicted AS GIVEN, pre-shell
   resolution — exactly where execute_command's gate sits. (RED->GREEN round
   caught the bug: gating the post-shell_argv line let a curl-shaped
   override through, because the egress guard matches PROGRAM WORDS like
   `curl`, not the powershell wrapper around them. The todo-4 learning
   "a string-pattern guard on the PROGRAM WORD is the correct seam"
   predicted this.)
3. Framework detection (day-one = cargo test + cargo nextest): Cargo.toml at
   the tested root -> cargo framework; a gated `cargo nextest --version`
   probe (15s ceiling) prefers `cargo nextest run --no-fail-fast`, falling
   back to `cargo test`. cargo resolves via $CARGO when set (tests/CI),
   else PATH (production).
4. Machine-readable format choice — EMPIRICALLY captured on this machine
   (nextest 0.9.144, stable libtest), before the parser was written:
   - `--message-format json` does NOT exist in 0.9.144 (possible values:
     human, libtest-json, libtest-json-plus);
   - libtest-json requires NEXTEST_EXPERIMENTAL_LIBTEST_JSON=1 (experimental
     flag — rejected as a day-one dependency);
   - nextest HUMAN output carries per-test statuses WITH durations
     (`PASS|FAIL|SKIP|ABORT|TIMEOUT [ 0.051s] (1/2) <binary> <test>`) and
     rides STDERR; parsing stops at the `Summary [` line so the failure
     recap never double-counts;
   - stable libtest text (`test NAME ... ok|FAILED|ignored`) carries
     per-test statuses WITHOUT per-test durations (JSON is nightly-only) —
     TestEntry.duration_ms is Option for exactly that honesty.
   nextest-ignored tests appear only in summary counts ("N skipped"), not as
   individual SKIP lines — documented in parse.rs.
5. Crash semantics: with nextest, an aborting test is DATA (process-per-test
   catches it: a failed entry with a duration). The typed crash error fires
   when the run failed with ZERO parseable per-test results (libtest crash,
   compile failure): "failed with exit code {code} and produced no parseable
   per-test results — stderr: {head}". A failing TEST is a report, never an
   error.
6. Permission tier: run_tests rides the approval stage as an aux tool
   (task-11 pattern) — no capability column maps it (capability_of
   ("run_tests") == None: no matrix toggle can EVER allow it), and the
   column execute_command maps to (Exec) is OFF in every preset. Under the
   default policy every call asks; an unanswered ask is refused and NOTHING
   executes. Never auto-allow — structural, asserted by tests.
7. Repo-local override refusal: {root}/.harness/run_tests.json is refused
   pre-execution with a typed error naming the file and pointing at the
   user-global config (HARNESS_TEST_COMMAND / DaemonConfig.test_command).
