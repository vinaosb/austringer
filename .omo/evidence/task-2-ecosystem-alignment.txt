## Scenario 1.5 — pre-existing SSE bug FOUND by the new test (root-cause fix in-scope)

First green attempt failed: the SSE stream ENDED right after hello_ack:
    FAIL sched_notification_surfaces_to_sse_client
    sse kinds: "stream ended before both kinds: data: {\"type\":\"hello_ack\",\"version\":2,\"last_event_id\":0}\n\n"
Root cause (pre-existing): handlers.rs `sse_events` built a throwaway inbound channel whose
sender dropped instantly; pump_client's select! arm then read closed-inbound as ClientGone and
terminated the connection immediately after replay + hello_ack — every /s/{sid}/events client
was cut off from live events. Never observed before because the only prior SSE consumer
(examples/qa_transcript.rs) reads the first 3 lines and disconnects.
Fix (handlers.rs): the pump task holds the inbound sender for the connection's lifetime
(`let _read_only = inbound_tx;` inside the spawned task), delivering the documented intent
("SSE is read-only: no inbound, no idle eviction"). pump_client/transport.rs untouched.
In-scope justification: the acceptance criterion ("a scheduled fixture run surfaces a sched
Notification to an attached SSE client") is untestable against a stream that dies post-ack.
