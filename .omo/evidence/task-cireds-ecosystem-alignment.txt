RED 1 - grammar_json_is_byte_pinned_to_the_const_table (windows CI)
================================================================
ROOT CAUSE (reproduced, not assumed):
  The test byte-compares serde_json::to_string_pretty (emits "\n") against
  include_str!("grammar.json") (reads WORKING-TREE bytes at compile time).
  The committed blob is LF (git ls-files --eol: i/lf), but windows CI
  runners default core.autocrlf=true, so the checkout rewrites the file to
  CRLF and include_str! bytes diverge. Repo had NO root .gitattributes.
  RED reproduction (local, autocrlf=true): converted the working copy to
  CRLF -> nextest FAIL with left: "...{\n..." right: "...{\r\n..." (exact
  CI symptom); run captured in transcript, exit 100.

FIX (chosen to keep the drift guarantee STRONG - byte-exact, not normalized):
  New root .gitattributes: "harness-daemon/src/grammar.json text eol=lf".
  Attribute eol=lf overrides autocrlf on EVERY platform, so every checkout
  is LF and the byte pin stays a true byte pin. (Alternative rejected:
  normalizing line endings inside the test would weaken the guarantee - a
  lone line-ending change would stop failing. JS/TS ports need nothing:
  they JSON.parse the file, whitespace-insensitive.) Test doc comment now
  carries the regression note (do NOT normalize in the test instead).

PROOF:
  - git check-attr text eol -> "text: set, eol: lf".
  - Deleted the working file, fresh `git checkout --` under local
    core.autocrlf=true (CI-equivalent): 0 CR bytes in the 1557-byte file.
  - Green: nextest grammar_json_is_byte_pinned -> 1 passed.
  - MUTATION SANITY CHECK (drift guarantee still strong): appended "X" to
    a help string in grammar.json -> test FAIL (exit 100) -> restored via
    git checkout. Any real content change still fails.

RED 3 - harness-media does not compile off-Windows (ubuntu/macos test matrix)
================================================================
ROOT CAUSE (reproduced by cross-check, not assumed):
  cargo check -p harness-media --all-targets --target x86_64-unknown-linux-gnu
  (target installed locally) reproduced the exact CI compile failure class:
    error: unused import: `std::io`        -> harness-media/src/tool/guard.rs:16
    error[E0599]: no method named `process_group` found for struct
        `std::process::Command`            -> harness-media/src/tool/executor.rs:197
    error: unused variable: `tool`         -> harness-media/src/tool/spawn.rs:83
  (1) use std::io is only needed by the windows attach_child; (2) the
  unix-only CommandExt trait was never imported, so the #[cfg(unix)]
  process_group(0) call had no method - compiled on Windows only because
  cfg strips the block; (3) the unix arm of attach_guard ignored `tool`
  (windows lints deny unused).

FIX (cfg-gated structure, matches the crate's existing per-OS pattern,
  no #[allow]):
  - guard.rs: io import moved fn-local into #[cfg(windows)] attach_child
    (next to the existing fn-local AsRawHandle import).
  - executor.rs: `#[cfg(unix)] use std::os::unix::process::CommandExt;`.
  - spawn.rs: attach_guard split into two cfg'd functions (windows keeps
    the tool-error mapping + param; unix takes only the child); call site
    in wait_bounded cfg'd to match.

PROOF (with an honestly-documented local verification harness):
  - Local cross-check obstruction: blake3 (required dep via harness-safety)
    builds unix .S assembly through cc-rs for the target triple; no linux
    cross C toolchain exists on this Windows box (no zig, no
    x86_64-linux-gnu-gcc; cargo-env.cmd's global CC=cl.exe cannot compile
    ELF asm). WORKAROUND for check-only verification: CC for the target
    pointed at a stub (%TEMP%\opencode\fakecc\cc.cmd) that creates empty
    object files for the -o/-Fo argument and exits 0. This is sound for
    `cargo check` ONLY because check performs no linking - the (empty)
    archives are never consumed; every Rust unit (lib, every feature lane
    via the dev-dep self-reference, all 39 integration test targets) is
    fully type-checked for the linux target.
  - cargo check -p harness-media --all-targets --target
    x86_64-unknown-linux-gnu -> exit 0 (re-run after the final fmt pass,
    40.8s, exit 0).
  - cargo check -p harness-media (lib only, linux target) -> exit 0.
  - Windows-side regression: full harness-media suite green in the 922-test
    nextest run (tool_executor kill-tree incl. timeout_kills_the_whole_tree_
    no_orphans PASS).

RESIDUAL UNCERTAINTY (documented per task contract):
  - The stub-CC harness proves COMPILATION (type-check + name resolution +
    borrow check for the linux cfg surface), not linking; CI's native gcc
    links for real. Any link-time issue (e.g. an extern symbol only a real
    blake3 archive provides) is outside what this check can see - none is
    expected (harness-media adds no externs of its own).
  - Adjacent pre-existing unix BEHAVIOR bug found during the audit, NOT
    fixed (out of scope: it compiles and CI's red was compile-only):
    harness-media/src/tool/spawn.rs find_program splits PATH on ';' - on

    name there (explicit-path overrides and the mocktool lane are
    unaffected). std::env::split_paths is the portable fix. Logged in
    issues.md for a follow-up.
